## Findings

### Q1 — PPTX2HTML pipeline architecture and complete feature coverage

**Big picture.** PPTX2HTML today is NOT the old browser/jQuery project the task description's "DOMParser? canvas? FileReader? JSZip?" phrasing anticipates — it is a from-scratch rewrite (last commit 2026-10-24) that is **zero-dependency, runs identically in Node 18+ and the browser, and contains no DOMParser, no canvas, no FileReader, no JSZip** (`package.json`: `"description": "... Pure JavaScript, zero runtime dependencies."`, empty `dependencies`, only devDeps esbuild/playwright/pngjs for build/test/verification). Grep across `src/` + `bin/` for `DOMParser|canvas|FileReader|JSZip` hits only the word "document" in comments; the only `document.*` usage is in `src/runtime/*.js` — the emitted player that runs in the *output* page, not in the converter. Node built-ins (`node:fs`, `node:path`) are imported only by `bin/pptx2html.js`; the library core `src/index.js` is environment-agnostic (takes `Uint8Array`, returns strings).

I verified this empirically: with **no `npm install`** (no node_modules), `node bin/pptx2html.js samples/sample.pptx` and `samples/features/objects.pptx` converted cleanly on bare Node v24 in this environment, producing self-contained HTML.

**Pipeline (unzip → model → HTML strings):**

1. **Entry** `src/index.js` — `convert(data, options)` = `loadPresentation()` then `renderDocument()`.
2. **OPC layer** `src/opc/package.js` — `OpcPackage` opens the zip (`src/util/zip.js` `ZipArchive`), reads `[Content_Types].xml` (Default/Override maps), exposes `partName`-keyed access: `bytes()/text()/xml()` (XML cached), relationship maps via `partDir + '_rels/' + file + '.rels'` with relative-target resolution (`resolvePartName` handles `../`, percent-decoding, external `TargetMode`), `mimeOf()` = magic-byte sniffing (`sniffMime` knows PNG/JPEG/GIF/BMP/TIFF/EMF/WMF/WebP/AVIF/HEIC/MP4/WebM/MP3/OGG/WMV/SVG…) → content-types → extension fallback (`MIME_BY_EXT`). `mainPart()` locates `/ppt/presentation.xml` via the package rel of type `officeDocument`.
3. **Zip** `src/util/zip.js` (217 lines) — own ZIP reader: EOCD scan, central directory, ZIP64 extra fields, CP437/UTF-8/UTF-16 name decoding, store+deflate via its own `src/util/inflate.js` (221 lines, hand-rolled `inflateRaw`), local-header recovery for truncated archives, OLE2 (legacy .ppt) detection with a clear error.
4. **XML** `src/util/xml.js` (385 lines) — own tokenizer producing a light DOM (`XNode` with `child/all/find/path/attr/num/bool/int` helpers). Namespaces are **canonicalized**: whatever prefixes a producer uses, names are rewritten to canonical `p:`, `a:`, `r:`, `c:`, `cx:`, `dgm:`, `p14:`, `p15:`, … via the `NS` map (both transitional and strict-OOXML namespace URIs). The rest of the codebase then addresses nodes as `'p:sp'`, `'a:solidFill'` etc. regardless of producer quirks.
5. **Model builders** `src/pptx/*` — `presentation.js` `loadPresentation()` builds the whole model: slide size from `p:sldSz`, masters in declaration order, slide list from `p:sldIdLst` + rels, sections (`p14:section`), custom shows, show settings from `presProps`, embedded fonts from `p:embeddedFontLst`, core properties. `makeDocHelpers` (`slide.js:954`) memoizes `Master`/`Layout`/`Theme` objects per part name.
6. **Slide builder** `src/pptx/slide.js` (976 lines) — `SlideBuilder.build()` renders the **three-layer element stack**: master `spTree` (unless `showMasterSp=0`) then layout `spTree` then slide `spTree`, each tagged `layer: master|layout|slide`. Element dispatch on `sp`/`cxnSp`/`pic`/`grpSp`/`graphicFrame`/`contentPart` (`element()`, line ~333). **Inheritance is a placeholder chain**: `[slide node, layout matching placeholder, master matching placeholder]` (`common()`, line ~357) — geometry/fill/text merge property-by-property down the chain; background resolves slide → layout → master (`background()`, line ~272). `mc:AlternateContent` branches resolved by `chooseAlternate`.
7. **Render layer** `src/render/*` — pure string emission via template literals. `document.js` `renderDocument()` assembles `<!DOCTYPE html>` with one `<style>` (`BASE_CSS` from `styles.js` + `@font-face` from `embedded-fonts.js`), slides joined as `<div class="pp-deck">`, player data as `<script type="application/json">`, optional inlined player source. `slide.js` emits absolute-positioned `.pp-el` divs (`boxCss`: left/top/width/height px + rotate/scale transforms); `shape.js` emits **inline SVG for geometry, strokes, arrowheads**; `paint.js` `svgPaint()` emits SVG `<defs>` gradients/patterns/picture fills with tiling; `text.js` emits semantic-ish `<p>`/`<span>` runs with inline CSS (`runCss`: font-size px, font-family stack, bold/italic, color, underline styles); `context.js` `RenderContext.url()` turns media into **data URIs** (`data:<mime>;base64,` + own base64 encoder `src/util/base64.js`) or a caller-supplied `mediaUrl` hook (used by the CLI's `--assets`).
8. **Runtime player** `src/runtime/player.js` (959 lines) + `src/generated/player-source.js` (player source inlined into the document at build time by `tools/build.mjs`) — keyboard/click/wheel/swipe navigation, speaker notes (`S` key), and evaluation of the timing tree (animations) and transitions inside the browser. This is the only browser-dependent code, and it ships *inside the output HTML*, not in the converter.

### Q2 — dom-to-pptx structure, exporter, conventions, round-trip notes

**Repo shape** (pnpm monorepo, `pnpm-workspace.yaml`, root `package.json` v2.1.2):

- `src/` — the library core (browser + node): `index.js` (`exportToPptx`, built on **pptxgenjs** + html2canvas), `node-exporter.js` (headless export via **puppeteer** driving a local Chrome/Edge/Firefox — NOT jsdom; it loads the HTML `page.goto(file://…)` and runs `window.domToPptx.exportToPptx` inside the page, pulling the pptx blob back to Node), `pptx-normalizer.js` (post-processes the pptxgenjs zip: strips dangling `[Content_Types].xml` overrides — "PowerPoint refuses to open files when Content_Types advertises parts not present" — reorders `a:pPr` children, and **injects hand-built `<p:timing>` animation XML and `<p:transition>` XML** from `src/animations/xml-templates.js` + `transitions.js`), `font-embedder.js` (embeds fonts via fonteditor-core/opentype.js + woff2 wasm), `image-processor.js`, `animations/css-parser.js` (parses their whitelist animation CSS classes into OOXML timing), `utils.js`.
- `bin/` — CLI entry points: `cli-main.js` (unified `dom-to-pptx` launcher: skills + exporter subcommands), `cli-exporter.js` (thin shebang wrapper re-exporting from) `cli-exporter-core.js` (the actual exporter: parseArgs/runExporter, separated so tests can import the core without a shebang), `cli-skills-installer.js` (interactive installer that scans standard dirs for Claude Code, Gemini CLI, Cursor, Windsurf, or installs locally to `.agent/skills`).
- `packages/dom-to-pptx-exporter/` — npm wrapper package whose `bin/cli.js` just calls `runExporter` from the root package (`packages/dom-to-pptx-exporter/bin/cli.js`).
- `packages/dom-to-pptx-skills/` — the skills package: `skills/dom-to-pptx-skill/SKILL.md` + `skills/dom-to-pptx-skill/reference/*.md` (9 reference docs) + `skills/examples/` (sample `.html` + produced `.pptx`).

**Exporter CLI** (`bin/cli-exporter-core.js` usage header, lines 1–19): `dom-to-pptx-exporter <htmlFile> [options]` with `--output/-o`, `--selector/-s` (default `.slide`), `--inject` (force-inject local browser bundle), `--title`, `--author`, `--width`/`--height` (inches, default 10×5.625 → 16:9), `--browser-width/--browser-height` (viewport px, default inches×192), `--template <path>` (base export on an existing .pptx's real master/layout) and `--base-layout`, `--no-pseudo` (skip `::before/::after`), `--help`.

**Conventions worth mirroring in our `skills/` layout** (CONTEXT decision 16 — standalone, credit where adapted):

- SKILL.md frontmatter keys `name` + imperative `description` ending in "Use whenever…" + `license` + `compatibility` — cheap, portable across agent hosts.
- `reference/` subfolder with small, single-purpose docs (whitelists, validation checklist, sample prompts, template library) linked from a table at the bottom of SKILL.md — directly transferable to `skills/pptx-to-html/` (we'd have our own: usage, fidelity-support matrix, validation).

- Worked `examples/` pairing source HTML with produced artifact — mirrors our round-trip demo need.
- Thin `bin/*.js` shebang wrappers over importable cores (`cli-exporter.js` vs `cli-exporter-core.js`) so tests can import CLI logic — a nice pattern for our `scripts/` if CLIs grow.

**Round-trip relevance (decision 13: LAND.E `presentation/slides.html` → dom-to-pptx → .pptx → our converter → HTML):**

- The .pptx that dom-to-pptx emits is **pptxgenjs-shaped**: default masters/layouts, absolutely positioned text boxes (from puppeteer-computed layout), images (gradients and complex CSS become SVG/PNG images via `generateGradientSVG`/html2canvas in `src/utils.js`/`index.js`), native tables, notesSlides from `data-pptx-notes`, and **injected hand-built `<p:timing>`/`<p:transition>` XML** (`pptx-normalizer.js:469`, `xml-templates.js`). So our converter WILL face real timing trees (their structure is documented in `src/animations/xml-templates.js` header: entrance = `p:set visibility` first then effect; click-groups `p:par/cTn` with `clickEffect`/`withEffect` node types) and standard transitions — exactly what PPTX2HTML's `pptx/timing.js`/`transition.js` parse.
- **Robustness requirement**: pptxgenjs's `[Content_Types].xml` historically advertises parts that aren't in the package (the reason `pptx-normalizer.js` exists). Our OPC reader must tolerate missing parts gracefully (PPTX2HTML's does — `has()` checks and per-slide try/catch with placeholder slides, `presentation.js` slide loop).
- The reference example deck structure is plain: `.slide-stage` flex column of absolutely-styled `.slide` divs (1920×1080), Google-Fonts `Inter`, `data-pptx-notes` optional (`packages/dom-to-pptx-skills/skills/examples/MonthlyWorkReport.html`, 8 slides).
- LAND.E's `presentation/slides.html` itself is **not present on this machine** (searched `~/Documents/development_projects` — no LAND.E checkout, only shippEdd/stevedore/nix-config-local); it lives in the LAND.E repo's presentation branch. Unanswered item — see Risks.

### Q3 — Zero-dep feasibility (node built-ins only)

**PPTX2HTML is itself the existence proof.** Its entire runtime — zip, inflate, XML, OOXML model, geometry, charts, metafiles, HTML emission — is dependency-free pure JS. For our Node-only converter the constraint is *looser* than theirs (they avoid node built-ins to stay browser-compatible; we may use `node:zlib`, `node:fs`, `node:path`, `Buffer`). What we must provide ourselves:

1. **Zip container reading** — parse EOCD/central directory/local headers (~150–200 lines; the full shape is visible in `src/util/zip.js`: EOCD scan with 64 KB comment window, ZIP64, name decoding, entry cache). **Shortcut: `node:zlib.inflateRawSync` replaces their entire 221-line `inflate.js`** — faster (native) and less code. Still hand-write the directory walker; also keep the local-header recovery path or at least a clear error for truncated decks, and the OLE2 magic check to fail .ppt (97-2003) files with a helpful message.
2. **OOXML XML parsing with namespaces** — Node has **no built-in XML parser** (no DOMParser server-side; `node:` has nothing for XML as of Node 24). Must hand-roll a tokenizer → light DOM with helpers (~200–400 lines, modeled on `src/util/xml.js`). The critical design they prove out: **canonicalize prefixes to a fixed NS map** (incl. both transitional and strict OOXML URIs, and the Microsoft extension namespaces p14/p15/a14/cx/dgm/dsp) so downstream code matches `'a:solidFill'` by name; plus `escapeXml` for emission. Entity handling must cover the standard five + numeric refs (their `decodeOoxmlEscapes` exists because Office writes some odd escapes).
3. **Image handling as data URIs** — trivial in Node: `Buffer.from(bytes).toString('base64')` replaces their hand-written base64; sniff mime from magic bytes (copy the `sniffMime` table approach from `src/opc/package.js`). Decisions needed on the expensive converters: EMF/WMF→SVG (797 lines in their `util/emf.js`) and TIFF→PNG (`util/tiff.js`); PNG size probing (`util/image.js`) only matters for intrinsic-size math.
4. **HTML/CSS emission without a DOM** — plain template-literal strings, exactly as `src/render/document.js`/`slide.js`/`text.js` do: one `<!DOCTYPE html>` doc, a single `<style>` block, absolutely positioned divs for placement, semantic tags inside (matches our CONTEXT decision 15 hybrid positioning — `.pp-el` absolute boxes with `<p>`/`<span>` inside is precisely that), inline SVG for complex DrawingML geometry (their `shape.js geometrySvg` + `paint.js svgPaint` pattern — gradients/patterns/picture-fills become SVG `<defs>` inside an absolutely-positioned `<svg>`), data-URI `<img>`. **Text layout is delegated to the browser via CSS** — no measurement code needed for the static document (their runtime refits autofit text with a small DOM walker, which we can defer or skip for phase 1 static output).
5. **What node:zlib does NOT give us** (the actual work): the OOXML model (masters/layouts/theme/inheritance chains), DrawingML geometry evaluation (187 preset guide formulas + custGeom — `geometry/presets.js` is generated tooling output `tools/build-presets.mjs`), color transforms, chart rendering, timing/transition parsing, and the player runtime if we want animations to *play* (static-output mode can emit timing data as JSON and skip the player entirely — their `--static` mode proves the seam: `options.player=false` → plain page, `render/document.js`).

**Riskiest parts (ranked):**

1. **Chart rendering** (their `chart/` is 2,429 lines) — axes, plots, labels, number formats. Mitigation: scope to the chart types the round-trip deck actually contains (dom-to-pptx decks contain none — it rasterizes/uses images; charts enter only via PPTX2HTML's sample decks).
2. **DrawingML geometry engine** — preset guide-formula evaluation. Mitigation: hardcode common presets (rect, roundRect, ellipse, line, chevron, arrow…) as path data; fall back to bbox approximation for exotic ones, reported via diagnostics.
3. **Text fidelity** — inheritance chains (7 levels in their `text.js` header comment: presentation default → master text styles → master placeholder → layout placeholder → shape list style → paragraph → run) and autofit. Mitigation: implement the chain structurally (it's bookkeeping, not math); use stored fontScale; accept minor metric drift.
4. **EMF/WMF + TIFF converters and EOT font de-obfuscation** — large, isolated; safe to defer behind diagnostics ("image part X not converted") since web formats cover the round-trip deck.
5. **Animations playback** — parsing `p:timing` is moderate (their `timing.js` is 538 lines); a full browser player is 959+ lines. Mitigation: parse and emit timing as data + optionally adapt the player later; static correctness first (matches CONTEXT priority order: core scripts first).
6. **SmartArt layout engine** (1,066 lines) — only needed for decks lacking the pre-rendered `dsp:` drawing; round-trip and pptxgenjs decks never contain SmartArt. Defer.

**Viable shortcuts (validated by upstream code):** string/template HTML+CSS+SVG emission (no DOM anywhere); `node:zlib` for inflate; `Buffer.toString('base64')` for data URIs; SVG as the universal escape hatch for geometry/fills/effects; strict-mode `--strict` + diagnostics channel instead of failing; per-slide try/catch with placeholder slides for robustness; `--slides 1,3-5` subset conversion for fast iteration.

## Recommendation

Plan the converter as a direct architectural mirror of PPTX2HTML's seam — `opc/` (zip+zlib, rels, content types) → `pptx/` model builders (presentation, slide w/ 3-layer inheritance, theme, color, fill, text, table, timing, transition) → `render/` string emitters (document, slide, shape-as-SVG, paint, text, table) — with node:zlib and Buffer replacing their hand-rolled inflate/base64. Make the parity target the enumerated feature list above, but stage it: parsing-model parity (everything) first with render fidelity tiered (text/fills/images/tables/inheritance full; charts and SmartArt minimal-with-diagnostics; EMF/WMF, TIFF, EOT fonts, and the animation *player* explicitly deferred) — the round-trip deck (decision 13) needs only the dom-to-pptx feature subset, which the staging covers early. Mirror the SKILL.md conventions (frontmatter keys, `reference/` doc table, copy-paste command block, examples pair) in `skills/pptx-to-html/`, and adopt their diagnostics + `--strict` CLI conventions; credit both MIT repos in README credits + inline where logic is adapted.

## Risks / unknowns

- **Parity ambiguity**: "everything PPTX2HTML does" (decision 7) includes the *interactive player* (animations/transitions playback, keyboard nav, notes viewer) and exotic converters (EMF/WMF, TIFF, EOT/MTX fonts, SmartArt engine) — the planner must decide whether "parity" means parse-and-approximate-with-diagnostics or pixel/playback equivalence; the latter is a multi-phase effort. The feature list above is the negotiation surface.
- **Scale reference**: PPTX2HTML's `src/` is ~12,000 lines excluding the generated player source. Even with shortcuts, our converter is a 3–6 kLOC first cut for the core subset; plans should be sized accordingly.
- **LAND.E `presentation/slides.html` was not inspectable from this machine** (no LAND.E checkout found under `~/Documents/development_projects`). The round-trip fixture's exact feature content (fonts, gradients, tables, animation classes) is therefore unverified; obtain the LAND.E repo/branch before planning the verification script. dom-to-pptx's bundled example (`skills/examples/MonthlyWorkReport.html`, 8 slides) is a workable stand-in.
- **Upstream volatility**: both repos are actively developing (PPTX2HTML HEAD is 4 weeks old; dom-to-pptx merged template support 4 weeks ago). Pin citations to commit `c8a96eb` (PPTX2HTML) and the v2.1.2 tag (dom-to-pptx) when re-checking.
- **pptxgenjs quirks in round-trip input**: `[Content_Types].xml` may advertise absent parts (the bug `pptx-normalizer.js` exists to fix — meaning older dom-to-pptx outputs still carry it); our OPC layer must not assume every advertised part exists. Also expect hand-built timing XML with exactly the structure documented in `src/animations/xml-templates.js`.
- **Node version**: PPTX2HTML targets Node ≥18; our `node:zlib`/`Buffer` usage is safe on any current LTS, but the plan should state the minimum (≥18 for stable `inflateRawSync` with Uint8Array).
- **Unanswered detail**: exact rendering mode for animations in our output (static list vs player) is a CONTEXT decision 12 area ("both modes") — research confirms the static/player seam exists upstream (`options.player=false`), so no blocker.
