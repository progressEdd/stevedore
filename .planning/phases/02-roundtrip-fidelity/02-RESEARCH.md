# Phase 02-roundtrip-fidelity Research

**Researched:** 2026-11-23 — inline

## Question

The five open questions from grilling (02-CONTEXT.md): (1) did the original round-trip run's source HTML reference non-local images (suspected root cause of the missing gif/video-slide exports 03/04/06/13/14/18); (2) which half of the loop loses the images — dom-to-pptx embedding or pptx-to-html rendering; (3) where does dom-to-pptx live, who owns it, and what does fixing it look like; (4) what tool produced the existing PNG exports and should both sides be regenerated by one tool; (5) per-slide causes of formatting drift on the 14 shared slides.

## Findings

### Q1 — The original run's HTML: relative refs that could not resolve where the file was loaded

- The original run's source is byte-provable: `reference/slides.html` is an **R100 rename** of the original `00-supporting-files/data/land-e-slides.html` (commit `9653da9` name-status; `git diff a011d3a:…/land-e-slides.html 9653da9:…/reference/slides.html` is empty), and it is md5-identical to the untouched LAND.E original (`2188a538…`, both copies). The committed round-trip pair (`tests/land-e-roundtrip.html`, `tests/land-e-slides.pptx`) are likewise R100 renames of the original outputs (`6b6c882`, `9653da9`).
- All 15 unique media refs in that HTML are **relative local paths** (`00-supporting-files/images/slides/…` — 10 raster/svg, 3 `.mp4`, plus 2 more pngs on slide 5; grep of `src="` at lines 2591–23326). There are **zero** `http(s)://` image URLs. So "non-local" is false in the literal URL sense, **true in effect**:
  - The original run loaded the HTML from the stevedore agent worktree — `01-07-PLAN.md` step 3: `node bin/cli-exporter.js '$WORKTREE/00-supporting-files/data/land-e-slides.html' …` — via puppeteer/file://.
  - At that commit (`a011d3a`, 2026-11-20) **no image/media files existed anywhere in this repo** (`git ls-tree -r a011d3a` → zero `.png/.svg/.mp4/...`). The media only landed three days later in `9653da9` (2026-11-23, "update supporting files so that reference slide photos and videos don't break"), placed at `reference/00-supporting-files/images/slides/` — exactly where the refs resolve **relative to `reference/slides.html`** (verified: all 15 refs resolve, none missing).
  - Those paths were local to the LAND.E project root (where `slides.html` sits beside `00-supporting-files/`), not to the stevedore worktree copy — the browser got 404s, so nothing could be embedded.
- Corollary: the media problem is plausibly a **staging problem, not a tooling bug** — re-running the export with `reference/slides.html` in place (decision 6's cheap diagnosis) should let the browser load every ref. Whether dom-to-pptx then *embeds* `<img>` and `<video>` is the separate question Q2/Q3 address.
- Note on terminology: the deck has **no `.gif` files at all** — the "gif/video" slides are 3 `.mp4` videos (slides 2, 13, 18) and image-only slides (3, 4, 6, 14, plus logo/photo slides 5, 15, 16, 17). The reference Marp pptx does contain one real gif (`ppt/media/image16.gif`, slide 15).

### Q2 — The image loss is on the dom-to-pptx side; but pptx-to-html has its own (newly found) text-fidelity bug

- `tests/land-e-slides.pptx` (148,820 bytes, 20 slides) contains **28 media parts, none of them source media**: 14 PNG+14 SVG pairs living only on slides 5, 8, 9, 10, 11, 17, sized 722 B–25.9 KB (e.g. `image-8-1.png` is a 595×13 strip). Inspecting them shows they are **rasterized CSS gradients**, not slide photos (`image-5-2.svg` is a 64×64 rounded gradient; `image-17-2.svg` even contains a malformed stop — `stop-color="linear-gradient(to top"` — an unparseable CSS string serialized verbatim).
- What a faithful conversion carries is on disk for comparison: `reference/slides.pptx` (11.1 MB, Marp-built) has **24 real media parts** — PNGs of 55 KB–2.2 MB on slides 3, 4, 5, 6, 14, 15, 16, 17, `media1–3.mp4` videos on slides 2/13/18, and `image16.gif` on slide 15 (rels of `ppt/slides/_rels/slideN.xml.rels`). The round-trip pptx has **zero** of these: no photos, no videos, no logos.
- The round-trip HTML (`tests/land-e-roundtrip.html`, 20 slides) references exactly the 14 SVG halves of those gradient pairs as `data:image/svg+xml;base64` `<img>`s — pptx-to-html **faithfully renders what the pptx contains**. Media slides 2, 3, 4, 6, 13, 14, 18 come out as empty shells (1 background element, zero text, zero images) because dom-to-pptx had nothing to place: those slides are media-only (empty headings + `.media-wrap`), so a failed image load leaves no content at all.
- **However** — a real pptx-to-html defect surfaced while grounding this: the committed and freshly regenerated HTML render **every** text span as `font-size:24px; font-family:"Calibri", Calibri, sans-serif; color:#000000` (800/800 spans), while the pptx's run properties carry the truth (e.g. slide 9 title: `sz="1414" b="1"`, `srgbClr val="1F2328"`, `<a:latin typeface="-apple-system">`). Root cause, reproduced in isolation: **`mergeProps` in `scripts/src/pptx/text.js:39–47` (stevedore @ `3388fcd`) iterates the property cascade most-specific-first and overwrites, so the *least*-specific level wins** — the presentation's `p:defaultTextStyle` (`sz="1800"` → 24 px, `+mn-lt` → theme minor = Calibri, scheme color tx1 → black) clobbers every run's own `a:rPr`. Probe: `buildTextBody` without `defaultTextStyle` in ctx → `{sz:19, color:'#1f2328', font:{latin:'-apple-system'}}`; with it → `{sz:24, color:null, font:{latin:'+mn-lt'}}`. This is our bug, on the `stevedore` branch, and it deflates text color/size/font fidelity deck-wide.
- Verdict: **missing images = dom-to-pptx (export) side; a large share of the formatting drift = both sides** (exporter loses class-driven styling, gradients, one heading; converter loses run-level styles via the cascade bug).

### Q3 — dom-to-pptx: third-party GitHub tool, scratch-cloned; nobody here owns it

- Upstream: **`github.com/atharva9167j/dom-to-pptx`, tag v2.1.2** (credited in `02-worktrees/stevedore/README.md:41`; pinned in `.planning/phases/01-pptx-to-html/01-07-PLAN.md`). It is not vendored, forked, or committed anywhere in this repo — phase 01 used it as a scratch clone outside the repo.
- Operational recipe (from `01-07-PLAN.md` steps 2–3 + `01-07-SUMMARY.md` deviations): clone to `${TMPDIR:-/tmp}/stevedore-roundtrip/dom-to-pptx`, `PUPPETEER_SKIP_DOWNLOAD=1 bun install`, **downgrade puppeteer to 23.11.1** (v2.1.2's `ensureBrowser` sync `executablePath()` check is broken by puppeteer 25, silently ignoring `PUPPETEER_EXECUTABLE_PATH`), **`bun run build` once** (the repo ships no `dist/`, CLI refuses to export without it), then run `node bin/cli-exporter.js <html> -o <pptx> -s section --title 'LAND.E' --width 13.333 --height 7.5` under `nix shell nixpkgs#chromium` with `PUPPETEER_EXECUTABLE_PATH` set.
- If the loss is on that side (it is, for media/headings/gradient quality), fix shapes:
  1. **No code change needed for the load failure** — stage the HTML where its relative refs resolve (`reference/` already qualifies; verified Q1). Re-run first (decision 6).
  2. If dom-to-pptx still drops loaded media (esp. `<video>` → pptx video parts, animated SVGs): a patch to the scratch clone evaporates on `/tmp` cleanup — durable options are a **pinned fork consumed like the stevedore skill** (subtree/vendor), a **patch file carried in stevedore's `scripts/`** applied at setup time, or an **upstream PR to atharva9167j/dom-to-pptx**. Choice is the user's; the reference pptx proves PowerPoint-shape output with mp4 parts is representable.
  3. Converter-side fixes (the `mergeProps` cascade inversion at minimum) are ours and land on `stevedore` via the phase PR flow (CONTEXT constraint).

### Q4 — The existing PNG exports: no recorded producer; not apples-to-apples

- **No script, config, or dependency in either repo produces PNGs.** Sweeps: this repo (only shippEdd skill shell scripts), `02-worktrees/stevedore` (comparator/converter only), and the LAND.E presentation worktree (markdown + decks only). No commit message names a tool; `712ad89` ("add LAND.E slide image exports…") added the images alone.
- The images fingerprint as **ad-hoc screen captures, not a deterministic exporter**: all 8-bit RGBA, but `reference-slides-images/` is 1768×995 with `17.png` off-size at **1767×995**, and `tests/11-19-images/` is 943×530 with `09.png` off-size at **830×603** — neither set is an exact 16:9 multiple of 1280×720 (Marp `--images png` emits exact 1280×720; `pdftoppm` emits exact-ratio sizes). The two sides also come from different sessions at different zooms (~138% vs ~74% of 1280×720).
- The tests set includes `02.png` — a **flat near-white blank** (ffmpeg signalstats: YAVG 235.2, saturation 0) — i.e. the capture covered at least one empty round-trip slide, so the six missing exports were not systematically excluded by a tool rule (why exactly those six were skipped is not recoverable from the repo; they are precisely the six empty-shell media slides).
- Implication: current side-by-side comparisons mix deck drift with capture drift (resolution, zoom, session). **Both sides should be regenerated by one deterministic export tool** — which is already decision 7's shape (export tooling in stevedore's `scripts/`, shipped with the skill). The luma-delta numbers below inherit this caveat.

## Recommendation

Sequence the phase as: (1) fix the `mergeProps` cascade inversion in `scripts/src/pptx/text.js` on the `stevedore` branch first — it is small, ours, and deflates drift on every slide at once; (2) re-run dom-to-pptx from `reference/slides.html` in place (all media refs resolve there) per decision 6 — this tests the staging hypothesis before any exporter surgery; (3) whatever media still fails to embed decides the dom-to-pptx question (fork/patch-file/upstream, per Q3 option 2) — budget for `<video>` being the hard case; (4) build the deterministic per-slide PNG exporter in stevedore's `scripts/` and regenerate **both** sides with it before producing the breakdown deliverable, so the per-slide table is apples-to-apples. Keep the comparator's image metric interpretation honest: 233% is over-count from gradient imgs, while the real image loss is invisible to it — the tightened ≤100% budget should count *resolved source media surviving*, not raw img counts.

## Risks / unknowns

- **Why exactly the six slides were skipped from `tests/11-19-images/` is unrecoverable** — no tool, script, or log exists; the blank-but-present `02.png` rules out a simple "skip empty slides" rule. Marked unknown; the question dissolves once exports are regenerated deterministically.
- **dom-to-pptx's behavior on *loaded* media is untested** — everything observed so far ran with unresolvable refs. Whether v2.1.2 embeds `<img>` bytes, rasterizes SVGs, or handles `<video>` at all is unknown until the decision-6 re-run happens; the reference pptx proves mp4 parts are representable, not that this tool writes them.
- **Puppeteer/toolchain fragility on NixOS** (puppeteer 23.11.1 pin, `bun run build`, nix chromium) is a repeat-setup tax every re-run pays; a scripted setup in stevedore's `scripts/` would remove it, but that's the user's call.
- The luma-delta figures mix capture drift with deck drift (Q4) — usable as a ranking only, not as acceptance numbers.
- Slide 5's dropped `<h1>` and slide 20's dropped snippet text are exporter-side text losses with no diagnosed mechanism (would need a dom-to-pptx debug run); the 01-07 summary already flagged slide 5 as "provably exporter-side."
- The reference pptx (`reference/slides.pptx`) was built by Marp, not dom-to-pptx — it bounds what a *faithful* deck carries, not what dom-to-pptx *can* carry.
